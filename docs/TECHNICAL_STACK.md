# Shift Studio 技術ノート

> **この文書は、実装の中身まで読みたい方向けです。**
> アプリの操作やシフト作成のために読む必要はありません。
> 利用手順は [README](../README.md) にあります。

本書は現在のソースに基づく設計の説明です。製品のロードマップや、法令適合・最適解取得時間の保証ではありません。

## 1. 技術スタック

| 層 | 採用技術 | このアプリでの用途 |
|---|---|---|
| 実行環境 | Python 3.12 | UI・入力処理・最適化・起動処理の共通言語 |
| Web UI | Streamlit | 日本語画面、編集表、複数選択、設定状態、ダウンロード |
| 最適化 | Google OR-Tools / CP-SAT | 必須条件を満たす勤務割当の探索と、配慮条件の改善 |
| 表データ | pandas | 職員・希望休等の表、CSV入出力、結果集計、表の装飾 |
| テスト | pytest / Streamlit AppTest | モデル・独立検査・画面操作・CSV連携の回帰検証 |
| Windows配布 | PyInstaller | Pythonと依存ライブラリを含む単一exeの生成 |
| 開発補助 | VS Code設定・タスク | 専用仮想環境、テスト探索、ローカル起動 |

依存範囲は [requirements.txt](../requirements.txt) と [requirements-build.txt](../requirements-build.txt) が正本です。
現状はStreamlit 1.42以上2未満、OR-Tools 9.12以上10未満、pandas 2.2以上3未満、pytest 8.3以上10未満、ビルド用PyInstaller 6.16以上7未満です。
これは互換範囲の指定であり、環境を完全再現するロックファイルではありません。

外部LLMや生成AIに勤務表を作らせる構成ではありません。勤務表の生成はローカルの制約最適化です。

## 2. 構成と責務

- [src/app.py](../src/app.py)：Streamlit画面、表の解析、設定状態、CSV・JSONの入出力。
- [src/optimizer.py](../src/optimizer.py)：データモデル、入力検証、不足の事前検査、CP-SATモデル、結果の独立検査。
- [src/launcher.py](../src/launcher.py)：開発用／配布exeの起動入口、空きポート選択、ブラウザー起動、セルフテスト。
- [tests](../tests)：モデル・画面・起動入口のテスト。

ソースは意図的にフラットな3ファイル構成です。Pythonパッケージとしての公開APIや、HTTP業務APIを提供する構成ではありません。
[pytest.ini](../pytest.ini) が `src` をインポートパスへ追加するため、テストでも直接 `optimizer` などをインポートします。

処理の流れは、**画面入力 → 型付きデータへの変換 → 入力検証 → 明らかな不足の事前検査 → 探索 → 独立検査 → 表示・出力** です。

## 3. CP-SATモデルの骨格

職員・勤務開始日・シフトの組ごとに、「割り当てる／割り当てない」を表す0/1変数を作ります。
勤務日の0/1変数と関連付け、1人1日1勤務までという条件を表現します。
シフトは1〜8種類の可変構成で、三交代専用のモデルにはしていません。

### 必須条件と配慮条件を分離する

**必須条件**には、必要人数、役職別配置、希望休、許可シフト、曜日固定、連続勤務、最低休息、月間時間の完全一致・上限などがあります。
任意で有効にする「前日より早い出勤の禁止」も、有効時は必須条件です。
これらはペナルティを払って破れる条件ではありません。両立しなければ解なしとなります。

一方、回避ペアと職員ごとの回避希望シフトは**ソフト条件**です。違反する割当を禁止せず、目的関数のコストへ加えます。
曜日固定で必須の勤務が回避希望と重なる場合は、必須勤務を守ったうえで回避コストが残ります。

### 目的関数の優先順位

1. 総配置数を少なくする。
2. 回避ペアと回避希望シフトの、重み付きコストの合計を少なくする。
3. 職員間の勤務日数差・各シフト回数差を少なくする。

別々の探索を順次行うのではなく、下位のコストの上限から係数を組み立て、単一の目的関数でこの優先順位を表現しています。
したがって、回避のためだけに総配置数を増やすことは優先しません。逆に、必須条件を満たすためなら最低人数を超える配置も行います。
「公平性」は勤務回数の差に関する指標であり、疲労や負担を包括的に評価する指標ではありません。

ペア回避は「同じ勤務開始日・同じシフト区分」に2人とも配置されたかで数えます。
実際の勤務時刻の重なりを直接評価しているわけではありません。シフト回避は該当する職員の回避希望シフトへの割当ごとに数えます。

## 4. 時間を扱う上での設計

### 分単位の整数

`ShiftTime` は勤務開始日0時からの開始分・終了分と休憩分を持ちます。
翌日終了は終了分を1440より大きくして表し、1勤務の長さは24時間以内とします。
休憩控除後の実労働時間と、開始から終了までの拘束時間は別物です。
労働時間集計には前者、勤務間休息には後者を使います。

個別勤務時刻の適用順は **日付指定 → 毎回の個別設定 → 標準時刻** です。
曜日固定は割当そのものを強制しますが、個別時刻設定はそのシフトに割り当てられた際の時刻を変更するだけです。

### 日付の基準を統一しすぎない

- 人数・役職・連勤・曜日固定は勤務開始日基準。
- 希望休は暦日基準。前日開始の勤務が希望休へ持ち越す場合も禁止。ただし00:00ちょうどの終了は可。
- 休息は実時間。翌日だけでなく中1日空く組み合わせも検査。
- 「前日より早い出勤の禁止」は、隣接する開始日の時計上の開始分を比較。休日で比較をリセットするが、休息の検査はリセットしない。
- 月間時間は勤務開始月へ全時間を計上。終了月への按分はしない。

月間指定時間は対象暦日数で日割りし、整数分に四捨五入した値へ**完全一致**させます。
月間上限は日割りしません。未設定と0分は区別し、0分の指定は勤務禁止です。

### 短時間勤務と必要人数

職員の開始・終了境界で標準シフト時間を区切り、各区間をカバーできる職員だけで最低人数を満たすよう制約を置きます。
「各シフト」の役職人数も区間ごとに検査します。「1日のどこか」の役職条件は、その開始日に配置される人数を数えます。

この検査は標準シフト時間内・同じシフト区分内に限ります。別区分の職員の借用、標準時間外の必要人数、休憩取得時刻や休憩中の代替配置はモデル化していません。

## 5. 結果をどう信頼するか

探索結果は `optimal`・`feasible`・`infeasible`・`unknown`・`invalid` を区別します。
制限時間内に見つからなかったことを、両立不可と同一視しません。
実行可能解が得られた場合も、目的関数について最適性を証明できたとは限りません。

得られた割当には `audit_schedule()` を必ず実行します。
これはソルバーの変数値をそのまま信用せず、出力された割当から必須条件を再確認する処理です。
ただし、一部の時刻解決等の共通関数は共有しており、完全に独立した別実装や形式証明ではありません。

探索は8ワーカー、乱数シード42の設定です。並列探索のため、同一入力でも同点の別解や異なる所要時間が生じ得ます。
入力条件の指紋には画面の表と設定を含め、入力を変えた後に古い結果や結果ダウンロードを表示しないようにしています。

## 6. 状態とデータの置き場所

Streamlitの再実行モデルを前提に、画面の編集状態は `session_state` に保持します。
永続DB・ユーザー認証・自動保存はありません。CSVはUTF-8 BOM付きで出力し、条件JSONは記録用です。JSONの再読込機能はありません。

勤務データを外部APIへ送って最適化する処理はありません。標準の待受先は127.0.0.1で、使用統計送信も無効化しています。
これは入力CSVや出力ファイルの安全な保管まで保証するものではありません。設定変更による外部公開や私有データのGit追加は別途防ぐ必要があります。

## 7. テストと配布

pytestでモデルの正常系・矛盾・境界・独立検査を、Streamlit AppTestで設定変更・生成・CSV連携を検証します。
テストデータは架空の職員です。テスト成功は実際の施設の運用条件や労働法令への適合保証ではありません。

[ShiftStudio.spec](../ShiftStudio.spec) と [build_exe.bat](../build_exe.bat) により、単一exeを作成します。
画面ソースやStreamlit資源を同梱し、凍結時はPyInstallerの展開先から解決します。
起動時には空きポートを選び、Streamlitの設定をロードしてからローカルサーバーを起動します。
exeは組み込みのセルフテストと実際のHTTP画面で別途検証します。署名や自動更新は実装していません。

## 8. 読み進めるなら

1. `Employee`・`Settings`・`ShiftTime`：入力をどう表現しているか。
2. `validate_inputs()`・`capacity_issues()`：入力不正と明らかな不足の区別。
3. `solve_schedule()`：必須条件と目的関数。
4. `audit_schedule()`：生成後に何を再検査するか。
5. [tests](../tests)：仕様の境界と、意図的に許可／禁止しているケース。

入口はすべて [src/optimizer.py](../src/optimizer.py) にあります。画面の動きに興味がある場合だけ [src/app.py](../src/app.py)、配布方法に興味がある場合だけ [src/launcher.py](../src/launcher.py) を読むと追いやすくなります。
